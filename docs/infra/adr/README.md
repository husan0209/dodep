## ADR-001: Выбор микросервисной архитектуры

**Статус:** Принят  
**Дата:** 2026-03-24  
**Автор:** Platform Team

### Контекст

Требуется создать гемблинг-платформу для 10M+ пользователей с требованиями:
- 500K DAU (Daily Active Users)
- p99 < 10ms на критическом пути
- 99.99% uptime
- Масштабирование по разным бизнес-доменам

### Решение

Выбрана **микросервисная архитектура** с разделением по бизнес-доменам:

```
┌─────────────────────────────────────────────────────────┐
│                    CLIENT LAYER                          │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐     │
│  │   Next.js   │  │   Flutter   │  │    Admin    │     │
│  │    (Web)    │  │  (Mobile)   │  │   (React)   │     │
│  └─────────────┘  └─────────────┘  └─────────────┘     │
└─────────────────────────────────────────────────────────┘
                          │
                          ▼
┌─────────────────────────────────────────────────────────┐
│                     EDGE LAYER                           │
│  ┌─────────────────────────────────────────────────┐   │
│  │        CloudFlare (WAF, CDN, DDoS)              │   │
│  └─────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────┘
                          │
                          ▼
┌─────────────────────────────────────────────────────────┐
│                   BACKEND LAYER                          │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐  │
│  │   Rust   │ │    Go    │ │  Python  │ │  Events  │  │
│  │ Critical │ │ Business │ │   ML     │ │  Stream  │  │
│  └──────────┘ └──────────┘ └──────────┘ └──────────┘  │
└─────────────────────────────────────────────────────────┘
```

### Альтернативы

1. **Монолит**
   - ✅ Проще в разработке
   - ❌ Не масштабируется горизонтально
   - ❌ Единая точка отказа
   - ❌ Сложнее деплой и откат

2. **Модульный монолит**
   - ✅ Лучшая модульность
   - ❌ Всё ещё единый деплой
   - ❌ Сложнее масштабировать команды

### Последствия

**Положительные:**
- Независимое масштабирование сервисов
- Разные технологии для разных задач
- Изоляция отказов
- Параллельная разработка командами

**Отрицательные:**
- Сложность распределённых транзакций
- Требуется service mesh
- Сложнее отладка (нужен distributed tracing)
- Больше операционных расходов

## ADR-002: Выбор языков программирования

**Статус:** Принят  
**Дата:** 2026-03-24  
**Автор:** Platform Team

### Контекст

Разные сервисы имеют разные требования:
- Betting Engine: максимальная производительность
- Auth/Payment: быстрая разработка
- ML: экосистема Python

### Решение

| Зона | Язык | Фреймворк | Обоснование |
|------|------|-----------|-------------|
| Критический путь | **Rust** | Axum + Tokio | Производительность, безопасность памяти |
| Бизнес-логика | **Go** | Fiber/Echo | Простота, скорость разработки |
| ML/Analytics | **Python** | FastAPI + XGBoost | ML экосистема |
| Frontend | **TypeScript** | Next.js 14 | Типобезопасность, SSR |

### Альтернативы

1. **Всё на Go**
   - ✅ Единый язык
   - ❌ Betting Engine будет медленнее на 30-50%

2. **Всё на Rust**
   - ✅ Максимальная производительность
   - ❌ Медленная разработка бизнес-сервисов
   - ❌ Сложнее найти разработчиков

### Последствия

**Положительные:**
- Оптимальное соотношение performance/velocity
- Лучший инструмент для каждой задачи

**Отрицательные:**
- Нужно знать 3+ языка
- Разные инструменты и практики
- Сложнее онбординг

## ADR-003: Выбор баз данных

**Статус:** Принят  
**Дата:** 2026-03-24  
**Автор:** Data Team

### Контекст

Требуется поддержка:
- OLTP транзакции (ставки, платежи)
- Кэширование (сессии, odds)
- OLAP аналитика (отчёты, ML)
- Event streaming (уведомления, аудит)

### Решение

| БД | Назначение | Обоснование |
|----|-----------|-------------|
| **PostgreSQL 16 + Citus** | Основная OLTP | Шардирование, ACID, надёжность |
| **DragonflyDB** | Кэш + сессии | Redis-compatible, быстрее в 25 раз |
| **ClickHouse** | OLAP аналитика | Быстрые агрегации на больших данных |
| **Redpanda** | Event streaming | Kafka-compatible, быстрее, проще |

### Альтернативы

1. **MongoDB**
   - ❌ Нет ACID транзакций на уровне кластера
   - ❌ Не подходит для финансовых операций

2. **Cassandra**
   - ❌ Сложнее в эксплуатации
   - ❌ Нет сложных запросов

3. **Redis вместо DragonflyDB**
   - ❌ Медленнее на multi-thread нагрузках
   - ❌ DragonflyDB полностью совместим

### Последствия

**Положительные:**
- Лучший инструмент для каждого use case
- Горизонтальное масштабирование
- Высокая производительность

**Отрицательные:**
- 4 разные БД для поддержки
- Сложность data consistency
- Нужна команда DBA

## ADR-004: Выбор облачного провайдера

**Статус:** Принят  
**Дата:** 2026-03-24  
**Автор:** DevOps Team

### Контекст

Требуется:
- Глобальное присутствие
- Compliance для гемблинга
- Поддержка Kubernetes
- Хорошая цена/качество

### Решение

**Основной выбор: AWS**

| Сервис | AWS | Обоснование |
|--------|-----|-------------|
| Kubernetes | EKS | Managed, надёжно |
| Базы данных | RDS + self-hosted | Баланс цена/контроль |
| Object storage | S3 | Стандарт индустрии |
| CDN | CloudFlare | Лучше чем CloudFront для гемблинга |

### Альтернативы

1. **GCP**
   - ✅ Лучше Kubernetes (GKE)
   - ✅ Дешевле egress
   - ❌ Меньше регионов для гемблинга

2. **Azure**
   - ❌ Сложнее pricing
   - ❌ Меньше compliance для гемблинга

### Последствия

**Положительные:**
- Широкий выбор сервисов
- Глобальное присутствие
- Хорошая документация

**Отрицательные:**
- Vendor lock-in
- Сложный billing
- Egress дорогой

## ADR-005: Выбор service mesh (Istio)

**Статус:** Принят  
**Дата:** 2026-03-24  
**Автор:** Platform Team

### Контекст

Требуется:
- mTLS между сервисами
- Observability (tracing, metrics)
- Traffic management (canary, rollback)
- Rate limiting

### Решение

**Istio** — полнофункциональный service mesh

### Альтернативы

1. **Linkerd**
   - ✅ Проще, легче
   - ❌ Меньше функций

2. **Consul Connect**
   - ✅ Проще настройка

### Последствия

**Положительные:**
- Полный контроль над трафиком
- Встроенная безопасность
- Богатая телеметрия

**Отрицательные:**
- Сложность настройки
- Overhead ~5-10% latency
- Требует экспертизы

## ADR-006: Выбор CI/CD платформы

**Статус:** Принят  
**Дата:** 2026-03-24  
**Автор:** DevOps Team

### Контекст

Требуется:
- Поддержка Rust, Go, Python, TypeScript
- Быстрые билды
- Интеграция с Kubernetes
- Canary deployments

### Решение

**GitHub Actions + ArgoCD + Argo Rollouts**

| Компонент | Технология | Обоснование |
|-----------|-----------|-------------|
| CI | GitHub Actions | Интеграция с GitHub, бесплатно для OSS |
| CD | ArgoCD | GitOps, declarative |
| Canary | Argo Rollouts | Progressive delivery |

### Альтернативы

1. **GitLab CI**
   - ✅ Всё в одном
   - ❌ Дороже для больших команд

2. **Jenkins**
   - ❌ Устаревшая архитектура
   - ❌ Сложнее поддержка

### Последствия

**Положительные:**
- GitOps workflow
- Автоматические rollback
- Audit trail всех деплоев

**Отрицательные:**
- Сложность настройки
- Нужно хранить secrets в GitHub

## ADR-007: Выбор стратегии деплоя (Canary)

**Статус:** Принят  
**Дата:** 2026-03-24  
**Автор:** Platform Team

### Контекст

Требуется минимизировать риск деплоя:
- Автоматический rollback при ошибках
- Постепенный rollout
- A/B тестирование

### Решение

**Canary deployments с Argo Rollouts**

```
Новая версия: 5% → 25% → 50% → 100%
              ↓      ↓      ↓      ↓
           анализ  анализ анализ  готово
```

### Альтернативы

1. **Blue-Green**
   - ✅ Быстрый rollback
   - ❌ Требует 2x ресурсов

2. **Recreate**
   - ❌ Downtime при деплое
   - ❌ Нет rollback

### Последствия

**Положительные:**
- Минимальный риск
- Автоматический rollback
- Можно тестировать на части трафика

**Отрицательные:**
- Сложнее настройка
- Дольше деплой (15-30 мин)

## ADR-008: Выбор observability стека

**Статус:** Принят  
**Дата:** 2026-03-24  
**Автор:** Observability Team

### Контекст

Требуется:
- Metrics с retention 90+ дней
- Логи с поиском < 3 сек
- Distributed tracing
- Alerting с эскалацией

### Решение

| Компонент | Технология | Обоснование |
|-----------|-----------|-------------|
| Metrics | VictoriaMetrics + Grafana | Дешевле Prometheus, лучше масштабирование |
| Logs | Vector → ClickHouse | Быстрый поиск, дешёвое хранение |
| Tracing | Jaeger + OpenTelemetry | Стандарт индустрии |
| Alerting | Grafana Alerting → PagerDuty | Интеграция с Grafana |

### Альтернативы

1. **ELK Stack**
   - ❌ Дороже в эксплуатации
   - ❌ Медленнее на больших объёмах

2. **Datadog/New Relic**
   - ❌ Очень дорого для 10M+ пользователей
   - ✅ Меньше операционных расходов

### Последствия

**Положительные:**
- Полный контроль
- Дешевле на масштабе
- Нет vendor lock-in

**Отрицательные:**
- Нужно поддерживать самим
- Требует команду observability

## ADR-009: Выбор стратегии кэширования

**Статус:** Принят  
**Дата:** 2026-03-24  
**Автор:** Platform Team

### Контекст

Требуется:
- Сессии пользователей
- Кэш odds (обновление < 1 сек)
- Rate limiting
- Distributed locks

### Решение

**DragonflyDB** — Redis-compatible, но быстрее

| Use case | TTL | Обоснование |
|----------|-----|-------------|
| Сессии | 24h | Пользователь остаётся залогиненным |
| Odds | 500ms | Частое обновление |
| Rate limits | 1m | Скользящее окно |
| Distributed locks | 30s | Защита от race conditions |

### Альтернативы

1. **Redis**
   - ❌ Single-threaded
   - ❌ Медленнее на multi-core

2. **Memcached**
   - ❌ Нет persistence
   - ❌ Нет сложных структур данных

### Последствия

**Положительные:**
- P99 < 1ms
- Горизонтальное масштабирование
- Совместимость с Redis клиентами

**Отрицательные:**
- Нужно инвалидировать кэш
- Возможны stale данные

## ADR-010: Выбор стратегии безопасности

**Статус:** Принят  
**Дата:** 2026-03-24  
**Автор:** Security Team

### Контекст

Требуется:
- Защита от DDoS
- WAF для OWASP Top-10
- Шифрование данных
- Compliance (GDPR, gambling licenses)

### Решение

**Multi-layer security**

```
┌─────────────────────────────────────────┐
│  CloudFlare (Edge)                       │
│  - DDoS protection                       │
│  - WAF (OWASP Top-10)                    │
│  - Rate limiting                         │
│  - Bot management                        │
└─────────────────────────────────────────┘
              │
              ▼
┌─────────────────────────────────────────┐
│  Istio Service Mesh (Internal)           │
│  - mTLS между сервисами                  │
│  - Authorization policies                │
│  - Traffic encryption                    │
└─────────────────────────────────────────┘
              │
              ▼
┌─────────────────────────────────────────┐
│  HashiCorp Vault (Secrets)               │
│  - Dynamic DB credentials                │
│  - Certificate management                │
│  - Encryption as a service               │
└─────────────────────────────────────────┘
```

### Альтернативы

1. **AWS WAF + Shield**
   - ❌ Дороже
   - ❌ Меньше функций для гемблинга

2. **Cert-manager вместо Vault**
   - ❌ Только сертификаты
   - ❌ Нет dynamic secrets

### Последствия

**Положительные:**
- Защита на всех уровнях
- Автоматическая ротация секретов
- Compliance ready

**Отрицательные:**
- Сложность настройки
- Требует security экспертизу
- Vault — ещё один сервис для поддержки

## Как создавать новые ADR

1. Создайте файл `docs/infra/adr/ADR-XXX-title.md`
2. Используйте этот шаблон:
   - Контекст
   - Решение
   - Альтернативы
   - Последствия
3. Отправьте PR для review
4. После acceptance добавьте в индекс
