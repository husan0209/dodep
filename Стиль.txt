## Вступление

Все три документа вместе покрывают примерно **65-70%** от production-ready спецификации. Каждый последующий документ добавлял глубину, но при этом создавал новые противоречия с предыдущими. Третий документ — самый ценный с точки зрения edge cases и архитектурных проблем, но он тоже имеет пробелы.

## СЛОЙ 1: ЧТО ДЕЙСТВИТЕЛЬНО СИЛЬНО ВО ВСЕХ ТРЁХ ДОКУМЕНТАХ

### Архитектурное разделение Casino / Sportsbook

Все три документа последовательно и правильно разделяют эти два потока. Это не просто «два раздела сайта» — это два фундаментально разных паттерна поведения пользователя:

**Casino-пользователь:**
- Решение принимает эмоционально
- Сессия импульсивная — зашёл, покрутил, ушёл или залип
- Ключевая метрика — время до первого спина
- Визуал решает

**Sports-пользователь:**
- Решение принимает аналитически
- Сессия целенаправленная — ищет конкретный матч или маркет
- Ключевая метрика — время до размещения ставки
- Данные решают

Все три документа это понимают. Это правильный фундамент.

### WebSocket для live-данных

Правильно выбрана технология. Правильно описана визуализация (зелёный/красный для изменения коэффициентов). Третий документ добавил reconnection strategy — это критически важно и часто забывается.

### Mobile First

90% трафика — мобильный. Все документы это учитывают. Tab bar, bottom sheet для купона, touch targets — всё на месте.

### Skeleton loading вместо спиннеров

Упомянуто во втором документе, подтверждено третьим. Это правильный паттерн для гемблинга, где пользователь нетерпелив и каждая секунда ожидания — потенциальный отказ.

## СЛОЙ 2: ПРОТИВОРЕЧИЯ МЕЖДУ ДОКУМЕНТАМИ

### Противоречие 1 — RTP

| Документ | Позиция |
|---|---|
| Doc 1 | Показывать RTP на карточке и странице игры |
| Doc 2 | Убрать RTP полностью, аргументация бизнес-логикой |
| Doc 3 | Компромисс: RTP в разделе «Правила игры» внизу страницы |

**Анализ:** Doc 3 нашёл правильный компромисс, но недоговорил. Решение должно быть привязано к **юрисдикции**:

- **UKGC (Великобритания):** RTP обязателен к отображению. Прятать нельзя
- **MGA (Мальта):** RTP должен быть доступен, но не обязательно на первом экране
- **Кюрасао:** Нет требований к отображению RTP
- **Нелицензированные рынки:** На усмотрение оператора

**Правильное решение:** Конфигурируемый флаг per jurisdiction. В коде — компонент RTP-badge, который показывается или скрывается в зависимости от geo-config. На странице игры RTP доступен всегда в раскрывающемся блоке «Информация об игре» — это удовлетворяет все юрисдикции и не мешает конверсии.

### Противоречие 2 — Поведение карточки игры при тапе (Mobile)

| Документ | Позиция |
|---|---|
| Doc 1 | Тап → промежуточный экран (bottom sheet) с кнопками «Играть» / «Демо» |
| Doc 2 | Тап → сразу открывает игру |
| Doc 3 | Согласен с Doc 1, аргументирует случайными нажатиями |

**Анализ:** Doc 3 прав, но не полностью. Нужно разделить по контексту:

- **Незалогиненный пользователь:** Тап → bottom sheet с «Демо» и «Войти для игры на деньги». Без вариантов — нельзя запускать реальную игру без авторизации
- **Залогиненный, первый визит:** Тап → bottom sheet. Пользователь ещё не знает интерфейс
- **Залогиненный, регулярный:** Опция в настройках «Быстрый запуск» — тап сразу открывает игру. Это для опытных пользователей, которые знают, что хотят

**Дополнение, которого нет ни в одном документе:** Long press на карточку → показать расширенную информацию (провайдер, волатильность, дата добавления, рейтинг среди игроков). Это для продвинутых пользователей, которые выбирают осознанно.

### Противоречие 3 — Параметры поиска

| Параметр | Doc 1 | Doc 2 | Doc 3 |
|---|---|---|---|
| Min символов | Не указано | 2-3 | 2 |
| Debounce | Не указано | 200-300ms | 250ms |

**Решение:** 2 символа, 250ms — как предлагает Doc 3. Но добавить:
- Для латиницы — 2 символа
- Для кириллицы — 2 символа
- Для иероглифов (CJK) — 1 символ (каждый иероглиф — самостоятельное слово)
- Для арабского — 2 символа, но учитывать RTL-направление ввода

### Противоречие 4 — Бесконечный скролл vs. пагинация

| Документ | Позиция |
|---|---|
| Doc 1 | Бесконечный скролл |
| Doc 2 | Виртуализированный список + «Загрузить ещё» |
| Doc 3 | Не затрагивает |

**Анализ:** Doc 2 прав. Чистый бесконечный скролл без виртуализации на каталоге из 5000+ игр — гарантированные проблемы производительности на мобильных устройствах среднего класса. Решение:

```
Виртуализированный список (react-window / vue-virtual-scroller)
+ Intersection Observer для подгрузки следующей порции (40 игр)
+ Якорь для возврата к позиции после навигации назад
+ Skeleton-заглушки для ещё не загруженных карточек
```

## СЛОЙ 3: EDGE CASES — ЧТО ОПИСАНО ПОВЕРХНОСТНО ИЛИ НЕТОЧНО

### 3.1. Потеря соединения во время игры в казино

Все документы говорят «показать overlay, переподключиться». Но реальность сложнее:

**Сценарий 1 — Потеря связи во время обычного спина:**
- Спин уже отправлен на сервер провайдера → результат определён
- Связь восстановилась → iframe перезагружается → провайдер восстанавливает сессию с результатом
- **UI платформы** не должен ничего делать — это зона ответственности провайдера
- Но баланс в хедере нужно обновить после восстановления → отдельный запрос баланса

**Сценарий 2 — Потеря связи во время бонусного раунда (Free Spins):**
- Критичнее, потому что бонусный раунд — серия спинов
- Провайдер хранит состояние на своей стороне
- При восстановлении — бонусный раунд продолжается с того места
- **Проблема для UI:** пользователь может подумать, что потерял бонус. Нужен toast: «Сессия восстановлена. Ваш бонусный раунд продолжается»

**Сценарий 3 — Потеря связи на стороне провайдера (не пользователя):**
- Провайдер упал, но интернет у пользователя работает
- iframe покажет ошибку провайдера — пользователь не поймёт что произошло
- **UI платформы** должен обнаружить это (health check провайдера) и показать своё сообщение: «Игра временно недоступна. Ваш баланс не затронут»
- Предложить другую игру того же типа

**Чего нет ни в одном документе:** Мониторинг состояния iframe. Если iframe не отвечает более 10 секунд (frozen tab, crash) — платформа должна показать overlay поверх iframe с опциями «Перезагрузить игру» и «Вернуться в лобби».

### 3.2. Race condition баланса

Doc 3 упоминает проблему расхождения баланса между хедером платформы и внутри iframe провайдера. Но не предлагает решение.

**Полное решение:**

```
Источник истины: сервер платформы (wallet service)

Поток данных:
1. Пользователь делает спин в iframe
2. Провайдер отправляет bet request → wallet service
3. Wallet service списывает → отвечает провайдеру
4. Провайдер показывает результат в iframe
5. Wallet service через WebSocket пушит новый баланс → хедер платформы

Задержка между шагом 4 и 5: 100-500ms
Это означает, что баланс в iframe обновится раньше, 
чем баланс в хедере.

UI-решение:
- При получении обновления баланса через WS — 
  анимация цифр (countup) от старого значения к новому
- Визуально скрывает задержку в 300-500ms
- Если расхождение >5 секунд — принудительный 
  запрос баланса через REST API
```

### 3.3. Купон — персистентность и edge cases

Doc 3 правильно поднял вопрос localStorage с TTL. Но есть тонкости:

**Мульти-вкладки:** Пользователь открыл сайт в двух вкладках. Добавил исход в купон в первой вкладке. Во второй — купон пустой. Решение:

```
BroadcastChannel API (современные браузеры)
или
StorageEvent listener (fallback)

При изменении купона в одной вкладке — 
все остальные синхронизируются через BroadcastChannel.
```

**Устаревшие исходы:** Пользователь добавил исход вчера, вернулся сегодня. Матч уже начался или завершился. Купон должен:
1. При загрузке — проверить актуальность каждого исхода через API
2. Неактуальные — пометить красным + причина («Матч завершён», «Маркет закрыт»)
3. Предложить удалить невалидные
4. Не блокировать весь купон — дать возможность поставить на оставшиеся валидные исходы

**Максимальное количество исходов:** Не определено ни в одном документе. Обычно 20-30 исходов для экспресса. UI должен показать предупреждение при приближении к лимиту и заблокировать добавление при достижении.

### 3.4. Депозит — незавершённая транзакция

Doc 3 спрашивает «что происходит при logout с незавершённой транзакцией». Ответ, которого нет:

**Сценарий:** Пользователь начал депозит через карту → перенаправлен на 3DS страницу банка → закрыл браузер/залогаутился.

```
Возможные состояния:
1. Транзакция pending на стороне PSP (платёжного провайдера)
2. Пользователь вернулся через час

Правильное поведение:
- При следующем логине проверить статус pending-транзакций
- Если транзакция успешна — зачислить баланс + toast-уведомление
- Если транзакция отклонена — уведомить
- Если транзакция всё ещё pending — показать статус в разделе транзакций
- Не позволять инициировать новый депозит пока есть pending (защита от двойного списания)
```

### 3.5. Кэшаут — технические нюансы

Doc 2 и Doc 3 описывают кэшаут, но поверхностно.

**Задержка принятия:** Пользователь нажал «Кэшаут 3 240₽», но за 200ms пока запрос шёл на сервер — коэффициенты изменились и кэшаут теперь 3 180₽.

```
Варианты поведения:
A) Отклонить кэшаут, показать новую сумму, 
   попросить подтвердить заново
   → Стандартный подход, но раздражает

B) Принять кэшаут по новой сумме автоматически 
   (если снижение <5%)
   → Быстрее, но пользователь может быть недоволен

C) Дать настройку: «Принимать кэшаут при 
   изменении суммы до X%»
   → Лучший UX, аналогично настройке 
   «Принять изменения коэффициентов» в купоне

Рекомендация: Вариант A по умолчанию, 
с опцией переключить на C в настройках.
```

**Частичный кэшаут — гранулярность:** Doc 2 показывает слайдер. Но не определено:
- Минимальная сумма частичного кэшаута (например не менее 10% от полного)
- Шаг слайдера (по 100₽? по 10₽? произвольная сумма?)
- Можно ли делать частичный кэшаут несколько раз на одну ставку

## СЛОЙ 4: ПОЛНОСТЬЮ ОТСУТСТВУЮЩИЕ БЛОКИ

### 4.1. Error State Design System

Ни один документ не описывает **систему состояний ошибок**. Это огромный пробел. Каждый компонент интерфейса имеет минимум 5 состояний:

```
1. Default (нормальное)
2. Loading (загрузка)
3. Empty (нет данных)
4. Error (ошибка)
5. Success (успех)
```

**Для каждого ключевого экрана нужно определить все состояния:**

**Каталог игр — Empty:**
```
┌──────────────────────────────┐
│                              │
│      🔍                      │
│  Ничего не найдено           │
│                              │
│  Попробуйте изменить         │
│  фильтры или поисковый       │
│  запрос                      │
│                              │
│  [Сбросить фильтры]          │
│  [Показать все игры]          │
└──────────────────────────────┘
```

**Каталог игр — Error:**
```
┌──────────────────────────────┐
│                              │
│      ⚠️                      │
│  Не удалось загрузить игры   │
│                              │
│  Проверьте соединение        │
│  и попробуйте снова          │
│                              │
│  [Повторить]                 │
└──────────────────────────────┘
```

**Купон — Error (ставка отклонена):**
```
┌──────────────────────────────┐
│  ❌ Ставка отклонена          │
│                              │
│  Причина: Коэффициент        │
│  изменился                   │
│                              │
│  Старый: 2.10 → Новый: 1.95 │
│                              │
│  [Принять новый кэф]         │
│  [Отменить ставку]           │
└──────────────────────────────┘
```

**Депозит — Error:**
```
┌──────────────────────────────┐
│  ❌ Платёж не прошёл          │
│                              │
│  Возможные причины:          │
│  • Недостаточно средств      │
│  • Карта заблокирована       │
│  • Превышен лимит            │
│                              │
│  [Попробовать снова]          │
│  [Выбрать другой метод]      │
│  [Связаться с поддержкой]    │
└──────────────────────────────┘
```

Таких состояний по платформе — десятки. Каждое должно быть спроектировано отдельно. Без этого разработчики будут импровизировать, и пользователь увидит «Something went wrong» — что абсолютно неприемлемо в гемблинге, где на кону реальные деньги.

### 4.2. Offline / Degraded State

Что видит пользователь когда интернет полностью пропал:

```
┌──────────────────────────────┐
│                              │
│      📡                      │
│  Нет соединения              │
│                              │
│  Данные на экране могут       │
│  быть неактуальны.           │
│  Ставки и игры недоступны.   │
│                              │
│  Проверьте подключение       │
│  к интернету.                │
│                              │
│  [⟳ Обновить]                │
│                              │
│  Баланс на момент            │
│  последнего обновления:      │
│  12 530₽ (5 мин назад)       │
└──────────────────────────────┘
```

**Что должно работать offline (PWA):**
- Просмотр истории ставок (кэшированной)
- Просмотр профиля
- Раздел «Правила» и «Ответственная игра»
- Показ последнего известного баланса с меткой времени

**Что не может работать offline:**
- Размещение ставок
- Запуск игр
- Депозит/Вывод
- Live-данные

### 4.3. Мультисессия (Multi-device)

Doc 3 упоминает синхронизацию между устройствами, но не определяет конфликтные сценарии.

**Сценарий:** Пользователь играет в слот на телефоне и одновременно открыл сайт на компьютере.

```
Проблемы:
1. Баланс — обновления с телефона (спины) должны 
   мгновенно отражаться на компьютере (через WS)

2. Одновременные депозиты — пользователь начал 
   депозит на обоих устройствах. 
   Первый прошёл, второй может привести к 
   превышению лимита. 
   Решение: lock на уровне wallet service

3. Одновременная игра в два слота — 
   допустимо ли это? 
   Большинство провайдеров разрешают только 
   одну активную сессию на игру. 
   Если пользователь открывает второй слот — 
   первый должен корректно завершиться

4. Logout на одном устройстве — 
   должен ли автоматически выходить на другом? 
   Обычно нет — сессии независимы. 
   Но смена пароля → инвалидация всех сессий
```

**Порядок списания ставок:** Это нигде не описано, но критически важно для UX. Обычно:
1. Сначала списываются реальные деньги
2. Когда реальные закончились — начинают списываться бонусные
3. Пользователь должен видеть, из какого баланса идёт списание

Некоторые платформы позволяют выбрать: «Играть на реальные» / «Играть на бонусные». Это UX-решение, которое нужно принять и задокументировать.

### 4.5. Push-уведомления — стратегия и UI

PWA поддерживает push-уведомления, но ни один документ не определяет:

**Запрос разрешения:**
```
Когда запрашивать:
❌ Сразу при первом визите — будет отклонён в 90% случаев
✅ После первого депозита или третьей сессии
✅ При подписке на событие («Уведомить о начале матча»)

Как запрашивать:
1. Сначала показать свой UI-элемент (не браузерный):
   «Хотите получать уведомления о результатах 
   ваших ставок и акциях?»
   [Да, включить] [Позже]

2. Только при нажатии «Да» — вызвать 
   браузерный Notification.requestPermission()
```

**Типы push-уведомлений:**

| Тип | Пример | Приоритет | Deep Link |
|---|---|---|---|
| Результат ставки | «✅ Ваша ставка выиграла! +5 230₽» | Высокий | Мои ставки |
| Начало матча | «⚽ Арсенал — Челси начинается через 15 мин» | Средний | Страница матча |
| Бонус доступен | «🎁 20 фриспинов ждут вас» | Средний | Бонусы |
| Промо | «🔥 Турнир с призовым фондом 1M₽» | Низкий | Промо-страница |
| Транзакция | «💰 Вывод 10 000₽ одобрен» | Высокий | Транзакции |

**Ограничения:**
- Не более 3 push в день (иначе пользователь отключит)
- Промо-push — не чаще 1 раза в день
- Транзакционные (результат ставки, вывод) — без ограничений
- Настройки push-категорий в профиле пользователя

### 4.6. Конструктор ставок (Bet Builder) — полная спецификация

Doc 3 правильно отметил, что Bet Builder упомянут, но не специфицирован. Это действительно самый сложный компонент.

```
┌──────────────────────────────────────┐
│  🔧 Конструктор ставки               │
│  Арсенал — Челси                     │
├──────────────────────────────────────┤

│  Ваши выборы:                        │
│                                      │
│  ✅ Победа Арсенала          ✕      │
│  ✅ Обе забьют — Да          ✕      │
│  ✅ Тотал угловых больше 9   ✕      │
│  ⚠️ Сака — забьёт           ✕      │
│     ↑ Снижает коэффициент            │
│       (коррелирует с «Победа         │
│        Арсенала»)                    │
│                                      │
│  Добавить выбор:                     │
│  [Результат ▼]                       │
│  [Голы ▼]                            │
│  [Угловые ▼]                         │
│  [Карточки ▼]                        │
│  [Игроки ▼]                          │
│                                      │
├──────────────────────────────────────┤
│  Итоговый коэффициент: 14.80        │
│  ⟳ Пересчитывается...               │
```

**Технические нюансы:**

- Пересчёт коэффициента при каждом добавлении/удалении выбора → запрос к серверу → задержка 500-2000ms → показывать спиннер рядом с коэффициентом
- Коррелированные исходы: сервер возвращает warnings, UI показывает их
- Некоторые комбинации невозможны (например «Победа 1» + «Победа 2» в одном матче) → серверная валидация + UI-блокировка
- Максимум выборов — обычно 6-12, зависит от провайдера маркетов
- Bet Builder обычно доступен только для prematch, не для live

## СЛОЙ 5: ПРОИЗВОДИТЕЛЬНОСТЬ — МЕТРИКИ И БЮДЖЕТЫ

Ни один документ не определяет **Performance Budget** — числовые ограничения, которым должен соответствовать интерфейс.

### Рекомендуемые метрики

| Метрика | Целевое значение | Критическое |
|---|---|---|
| First Contentful Paint (FCP) | < 1.5s | > 3s — неприемлемо |
| Largest Contentful Paint (LCP) | < 2.5s | > 4s — неприемлемо |
| First Input Delay (FID) | < 100ms | > 300ms — неприемлемо |
| Cumulative Layout Shift (CLS) | < 0.1 | > 0.25 — неприемлемо |
| Time to Interactive (TTI) | < 3s | > 5s — неприемлемо |
| Размер JS бандла (gzipped) | < 300KB initial | > 500KB — проблема |
| Размер изображений на первом экране | < 500KB | > 1MB — проблема |
| WebSocket latency | < 200ms | > 500ms — влияет на live |
| API response time (p95) | < 300ms | > 1s — неприемлемо |

### Оптимизации, которые должны быть прописаны

**Изображения (обложки игр):**
```
- Формат: WebP с JPEG fallback
- Lazy loading: все карточки ниже первого экрана
- Responsive: 3 размера (150px, 300px, 600px по ширине)
- CDN с географическим кэшированием
- Blur placeholder (LQIP) до загрузки полного изображения
```

**JavaScript:**
```
- Code splitting по маршрутам:
  /casino — загружает только casino-модуль
  /sports — загружает только sports-модуль
  Общий код (хедер, авторизация, баланс) — в shared chunk

- Tree shaking для удаления неиспользуемого кода
- Dynamic import для модальных окон и попапов
```

**Шрифты:**
```
- Preload для основного шрифта (Inter)
- font-display: swap — текст виден сразу, шрифт подгружается
- Subset: только нужные глифы для каждого языка
- Формат: WOFF2
```

## СЛОЙ 6: ACCESSIBILITY (ДОСТУПНОСТЬ) — РАСШИРЕНИЕ

Doc 2 касается accessibility минимально. Для гемблинга это не просто «хороший тон» — некоторые регуляторы (UKGC) требуют минимальный уровень доступности.

### Обязательные требования

**Контрастность:**
- Текст на тёмном фоне: минимум 4.5:1 для обычного текста, 3:1 для крупного (18px+)
- Кнопки коэффициентов: текст должен читаться на активном и неактивном состоянии
- Проблемная зона: золотой текст (#D4AF37) на тёмном фоне (#1A1A2E) — нужно проверить конкретно эту пару. Контрастность #D4AF37 на #1A1A2E = ~6.5:1 — проходит, но едва. При уменьшении размера шрифта может стать нечитаемым

**Клавиатурная навигация:**
```
Tab — переход между интерактивными элементами
Enter/Space — активация кнопки
Escape — закрытие модалки/попапа
Arrow Keys — навигация внутри списков (виды спорта, маркеты)

Focus ring: 2px solid #00FF9F (заметный на тёмном фоне)
Focus trap: в модальных окнах фокус не выходит за пределы
```

**Screen reader:**
```
- aria-label для иконок без текста (⭐, 🔍, 👁)
- aria-live="polite" для обновления баланса
- aria-live="assertive" для ошибок (ставка отклонена)
- role="alert" для критических уведомлений
- Коэффициенты: не просто «2.10», а 
  aria-label="Победа Арсенала, коэффициент 2.10"
```

**Размеры и отступы:**
```
- Touch target: 44x44px минимум (Apple HIG) / 48x48dp (Material Design)
- Расстояние между кнопками коэффициентов: минимум 8px
- Кнопки в купоне (удалить, изменить сумму): не менее 36x36px
```

## СЛОЙ 7: ЛОКАЛИЗАЦИЯ — ПРАКТИЧЕСКИЕ НЮАНСЫ

### RTL (Right-to-Left) — Арабский, Иврит

Если платформа работает на Ближнем Востоке — нужна полная RTL-поддержка:

```
LTR (стандарт):
┌────────────┬──────────────────┬────────────┐
│  Спорт     │    Линия         │   Купон    │
└────────────┴──────────────────┴────────────┘

RTL (арабский):
┌────────────┬──────────────────┬────────────┐
│   Купон    │    Линия         │  Спорт     │
└────────────┴──────────────────┴────────────┘

Что меняется:
- Направление текста
- Порядок колонок
- Позиция иконок (стрелки, галочки)
- Направление свайпа
- Позиция скроллбаров
- Alignment чисел (остаются LTR даже в RTL!)
```

**Числа в RTL:** Критический нюанс — арабские числа в Ближневосточном контексте могут быть:
- Западные (1, 2, 3) — используются в большинстве гемблинг-платформ
- Восточно-арабские (١, ٢, ٣) — некоторые рынки предпочитают
- Нужен конфиг на уровне локали

### Длина текста

```
Английский: "Deposit"    (7 символов)
Русский:    "Пополнить"  (9 символов)
Немецкий:   "Einzahlung" (10 символов)
Финский:    "Tallettaminen" (13 символов)

Кнопка, которая идеально вмещает "Deposit", 
будет обрезать "Tallettaminen".

Решение:
- Минимальная ширина кнопок — по самому длинному языку
- Или: text-overflow: ellipsis + tooltip
- Или: адаптивный размер шрифта (clamp())
- Тестирование UI на всех поддерживаемых языках — обязательно
```

### Культурные различия

| Элемент | Европа | Азия | Латинская Америка |
|---|---|---|---|
| Популярный спорт | Футбол, теннис | Крикет, бадминтон, E-sports | Футбол, бейсбол |
| Цвет «удачи» | Зелёный | Красный (Китай), Золотой | Зелёный |
| Формат даты | DD.MM.YYYY | YYYY/MM/DD | DD/MM/YYYY |
| Разделитель тысяч | 1.000 или 1 000 | 1,000 | 1.000 |
| Платёжные методы | Карты, Apple Pay | UPI, GCash, local wallets | PIX, Boleto |

## СЛОЙ 8: ЮРИДИЧЕСКИЕ ТРЕБОВАНИЯ К ИНТЕРФЕЙСУ

### По юрисдикциям

**UKGC (Великобритания):**
- Возрастная верификация до первого депозита (жёсткая)
- RTP должен быть доступен
- Ответственная игра — на каждой странице
- Запрет auto-play в слотах (или жёсткие ограничения)
- Net deposit tracker обязателен
- Запрет использования кредитных карт для депозита
- Time-out и self-exclusion — легкодоступны

**MGA (Мальта):**
- Panic button (мгновенный тайм-аут) — на видном месте
- Reality check каждые 60 минут (конфигурируемо пользователем)
- Баланс всегда видим
- Разделение реальных и бонусных средств

**Кюрасао:**
- Минимальные требования к UI
- Лого лицензиата в футере
- Ссылка на правила

**Каждая юрисдикция — отдельная конфигурация UI.** Нужна система feature flags, которая включает/выключает элементы интерфейса в зависимости от лицензии и гео пользователя.
