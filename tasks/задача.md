## Контекст

Нужно реализовать партнерскую программу для платформы `Opus Casino`, где:

- партнером может стать любой игрок платформы;
- игрок включает партнерский режим и получает уникальную реферальную ссылку;
- у партнера появляется отдельный кабинет внутри продукта;
- партнер получает процент не от оборота и не за сам факт регистрации приведенного игрока, а от чистой прибыли платформы;
- модель расчета: `revshare from NGR`;
- админка должна позволять управлять комиссионными планами и процентом партнера;
- `RTP` не должен использоваться как механизм управления партнерской комиссией.

## Важное уточнение

### Не путать RTP и партнерский процент

- `RTP` в казино = theoretical return to player, показатель игры/провайдера.
- `Partner commission` = доля партнера от `NGR`.
- Для affiliate-системы нужно управлять `commission_plan`, `commission_rate`, `hold_period`, `min_payout`, `approval_mode`, но не `RTP`.

Правильная бизнес-модель для этой задачи:

- `revshare from NGR`
- пример: `affiliate_commission = max(0, NGR * 0.50)`

## Бизнес-цель

Сделать встроенную партнерскую программу, в которой:

- любой пользователь может подать заявку на участие;
- после approve получает affiliate-профиль и referral-link;
- приводит новых игроков по ссылке;
- система отслеживает путь `click -> registration -> FTD -> activity`;
- комиссия считается автоматически на основании реальной прибыли платформы;
- у партнера есть прозрачный кабинет со статистикой, начислениями и выплатами;
- у админов есть полный контроль над планами, корректировками и выплатами.

## Основная финансовая модель

### Ключевые определения

- `FTD` = first-time deposit.
- `GGR` = gross gaming revenue.
- `NGR` = net gaming revenue.
- `RevShare` = процент партнера от `NGR`.

### Формулы

#### Casino GGR

```text
GGR = total_bets - total_wins
```

#### Sports GGR

```text
GGR = settled_stakes - payouts - refunds - voids - cashout_adjustments
```

#### NGR

```text
NGR = GGR
    - bonuses
    - payment_fees
    - chargebacks
    - fraud_writeoffs
    - taxes
    - manual_adjustments
```

#### Комиссия партнера

```text
affiliate_commission = max(0, NGR * commission_rate)
```

Для MVP:

- использовать `max(0, ...)`;
- не вводить negative carryover на первом релизе;
- считать только по `settled` и финализированным данным.

## Ограничения и правила домена

### Обязательные правила

- один игрок может быть привязан только к одному партнеру;
- self-referral запрещен;
- один и тот же payment instrument не может безопасно участвовать и как player-source, и как affiliate payout destination без отдельной проверки;
- совпадение по device, IP cluster, payment method, KYC identity должно поднимать fraud flag;
- комиссия не должна становиться `available` мгновенно;
- между `accrued` и `available` должен быть `hold_period`;
- выплата партнеру должна идти через отдельный payout flow;
- партнерские деньги нельзя смешивать с игровым балансом без явного решения и отдельного учета.

### Что не делать в MVP

- не делать multi-level/sub-affiliate;
- не делать instant payout;
- не смешивать affiliate wallet с player wallet;
- не использовать RTP как рычаг affiliate-логики;
- не делать auto-approve без review.

## Рекомендуемая модель запуска

### Режим MVP

- любой игрок может подать заявку на affiliate-режим;
- статус заявки: `pending_review`;
- после проверки админом статус меняется на `active`;
- после активации создается affiliate-profile и referral-code;
- начисления считаются автоматически;
- вывод доступен только после:
  - KYC;
  - anti-fraud checks;
  - прохождения hold period;
  - достижения min payout threshold.

### Рекомендации по дефолтным настройкам

- `approval_mode = manual`
- `commission_rate_default = 20%`
- `special_rate = 35%-50%` только для вручную одобренных партнеров
- `hold_period = 14-30 days`
- `min_payout = 100 USD equivalent`
- `payout_schedule = monthly`

## Пользовательский сценарий

### Сценарий партнера

1. Игрок включает/запрашивает партнерскую программу.
2. Система создает заявку на affiliate enrollment.
3. Админ одобряет заявку.
4. Игрок получает:
   - referral code;
   - referral link;
   - affiliate dashboard;
   - payout settings.
5. Новый пользователь кликает по ссылке партнера.
6. Система сохраняет click attribution.
7. Новый пользователь регистрируется и привязывается к партнеру.
8. Новый пользователь делает FTD.
9. Пользователь играет.
10. Система рассчитывает GGR -> NGR -> commission.
11. Комиссия попадает в `pending`.
12. После hold period комиссия становится `available`.
13. Партнер запрашивает payout.
14. Админ/финансовый процесс подтверждает выплату.

## Архитектурное решение

### Новый сервис

Нужен отдельный `Affiliate Service` на Go.

Причины:

- домен богатый и финансово чувствительный;
- есть свой lifecycle;
- есть свои правила anti-fraud;
- есть payouts, adjustments, plans, attribution;
- есть свой кабинет и админские операции.

### Взаимодействие с текущими сервисами

#### Affiliate Service

Хранит и управляет:

- affiliate profiles;
- enrollment requests;
- referral links and campaigns;
- attribution;
- earnings;
- adjustments;
- payouts;
- payout methods;
- affiliate fraud flags.

#### User Service

Расширяется полями и логикой:

- `affiliate_status`
- `affiliate_enabled`
- `referred_by`
- `referral_code`

#### Payment Service

Нужен для payout flow партнерам:

- bank transfer;
- crypto payout;
- e-wallet payout.

Важно:

- payout партнера не должен быть тем же самым потоком, что обычный вывод игрока, без доменных ограничений;
- можно переиспользовать PSP-интеграции, но не смешивать бизнес-смыслы.

#### Wallet Core

Нужен отдельный ledger/accounting для affiliate earnings:

- accrued;
- pending;
- available;
- paid;
- reversed;
- adjusted.

#### ClickHouse

Нужен для:

- affiliate dashboards;
- агрегатов по дням/неделям/месяцам;
- LTV и cohort analytics;
- conversion funnels;
- fraud analytics.

#### Redpanda

Нужна событийная шина для:

- clicks;
- registration attribution;
- FTD;
- GGR/NGR aggregates;
- commission accrual;
- payout requested/paid.

## Что считать правильным бизнес-решением

- делать `revshare from NGR`;
- партнеру платить только от реальной прибыли;
- процент задавать через `commission plan`;
- `50%` допустимо как отдельный план, но не как дефолт для всех;
- не управлять партнеркой через `RTP`;
- не смешивать affiliate earnings с обычным player balance на MVP;
- payout партнера делать отдельным финансовым контуром.

## Короткий итог

Нужно реализовать полноценную affiliate-систему уровня gambling platform, а не просто поле `referral_code`.

Базовая модель:

- игрок -> заявка на affiliate;
- approve -> affiliate profile;
- unique referral link;
- click attribution;
- registration + FTD binding;
- GGR -> NGR -> revshare;
- partner dashboard;
- admin management;
- anti-fraud;
- payout flow;
- audit and analytics.
